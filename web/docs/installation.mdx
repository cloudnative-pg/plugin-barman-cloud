# Installation

:::important
1. The plugin **must** be installed in the same namespace as the CloudNativePG
   operator (typically `cnpg-system`).

2. Keep in mind that the operator's **listening namespaces** may differ from its
   installation namespace. Double-check this to avoid configuration issues.
:::

## Verifying the Requirements

Before installing the plugin, make sure the [requirements](intro.md#requirements) are met.

### CloudNativePG Version

Ensure you're running a version of CloudNativePG that is compatible with the
plugin. If installed in the default `cnpg-system` namespace, you can verify the
version with:

```sh
kubectl get deployment -n cnpg-system cnpg-controller-manager \
  -o jsonpath="{.spec.template.spec.containers[*].image}"
```

Example output:

```output
ghcr.io/cloudnative-pg/cloudnative-pg:1.30.1
```

The version **must be 1.30 or newer**.

### cert-manager

Use the [cmctl](https://cert-manager.io/docs/reference/cmctl/#installation)
tool to confirm that `cert-manager` is installed and available:

```sh
cmctl check api
```

Example output:

```output
The cert-manager API is ready
```

Both checks are required before proceeding with the installation.

The plugin is published on [OperatorHub](https://operatorhub.io/operator/plugin-barman-cloud)
and can be installed with the [Operator Lifecycle Manager](https://olm.operatorframework.io/)
(OLM), either from the OpenShift web console or by creating a `Subscription`.

:::important
Install the plugin in the **same namespace as the CloudNativePG operator**. 
If CloudNativePG was also installed through OLM, use the namespace of its
`Subscription` (for example `operators`).
:::

Create a `Subscription` for the plugin.
The example below uses the `operatorhubio-catalog`
catalog source shipped with upstream OLM:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: plugin-barman-cloud
  namespace: <cnpg namespace>
spec:
  name: plugin-barman-cloud
  source: operatorhubio-catalog
  sourceNamespace: olm
```

Wait for the `ClusterServiceVersion` to reach the `Succeeded` phase:

```sh
kubectl -n <cnpg namespace> get csv
```

### Creating the TLS certificates

An OLM bundle cannot contain cert-manager resources, so, unlike the other
installation methods, **the plugin's TLS secrets are not created for you**. 
The plugin pod starts without them, but CloudNativePG cannot register the plugin,
and clusters that use it report an unknown plugin, until both secrets exist in
the plugin's namespace:

- `barman-cloud-server-tls`
- `barman-cloud-client-tls`

If cert-manager is installed, create them with the following resources:

```yaml
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: selfsigned-issuer
spec:
  selfSigned: {}
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: barman-cloud-server
spec:
  secretName: barman-cloud-server-tls
  commonName: barman-cloud
  dnsNames:
    - barman-cloud
  usages:
    - server auth
  issuerRef:
    name: selfsigned-issuer
    kind: Issuer
    group: cert-manager.io
---
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: barman-cloud-client
spec:
  secretName: barman-cloud-client-tls
  commonName: barman-cloud-client
  usages:
    - client auth
  issuerRef:
    name: selfsigned-issuer
    kind: Issuer
    group: cert-manager.io
```

```sh
kubectl apply -n <cnpg namespace> -f certificates.yaml
```

The plugin loads the certificates on every TLS handshake, so it starts serving
as soon as the secrets exist, without a restart. You can also provide the
secrets by other means, as long as they have the same names and contain the
`tls.crt` and `tls.key` keys.

Finally, check that the deployment is up and running:

```sh
kubectl -n <cnpg namespace> rollout status deploy/barman-cloud
```

Example output:

```output
deployment "barman-cloud" successfully rolled out
```

## Running Multiple Replicas

The plugin Deployment can run with more than one replica for high
availability. Every replica serves the gRPC interface used by the CloudNativePG
operator, so the `barman-cloud` Service load-balances requests across all
ready pods. The `ObjectStore` controller uses leader election, so only one
replica reconciles `ObjectStore` resources at a time; the others take over
automatically if the leader is lost.

To scale the plugin:

```sh
kubectl -n cnpg-system scale deploy/barman-cloud --replicas=2
```

The Deployment keeps the `Recreate` strategy: during an upgrade all replicas
are replaced together, so the plugin is briefly unavailable regardless of the
replica count. Multiple replicas protect against pod or node loss, not against
upgrade downtime.

## Restricting the Watched Namespaces

By default the plugin operator works on every namespace. To limit it, set the
`WATCH_NAMESPACE` environment variable on the plugin Deployment to a
comma-separated list of namespaces:

```sh
kubectl -n cnpg-system set env deploy/barman-cloud WATCH_NAMESPACE=app1,app2
```

The plugin then only handles `Cluster` and `ObjectStore` resources in those
namespaces. A `Cluster` in any other namespace fails with an error when it
uses the plugin. When the variable is unset or empty, all namespaces are
watched.

The variable does not change the RBAC rules that come with the installation.
To drop the cluster-wide permissions, grant the plugin a namespaced `Role` and
`RoleBinding` in each listed namespace. Without them in every listed
namespace, the plugin cannot work.
